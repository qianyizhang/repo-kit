# Progressive technical walkthroughs

- **Goal** · Explain a mechanism across connected cases and actions. Use `show-me` to select evidence/views and [UI/UX](ui-ux.md) for interaction design.
- **Encounter** · A question, concrete case, meaningful action, observable consequence and route onward or back.

## Five rules

| Goal | Outcome |
| --- | --- |
| Whole system, bounded action | Overview, exploded view or grouped outcomes show how the system fits. One primary action and controls scoped to the current question. |
| Terms by role | Point to what each term does before its first control or claim. Keep names aligned across text, marks and controls. Reintroduce its role in new contexts. Disclose exact source names and background separately. Equal positions or values can carry different roles. |
| Visible consequence | State what the action reveals. Change one meaningful input. Show input and effect together, including what stays fixed and why. Match cases, moments, orientation and scale unless their difference is the question. Explain overlap or stillness. |
| Reinforcement through reuse | Alternate whole and detail. Apply the concept visibly to a familiar stage, then another case. Locate close views in the overview and keep them stable while scrubbing. |
| Reversible routes | Recommended story, nearby questions and a small map of position, route and neighbors. Name why each edge matters. Shared encounters preserve route-specific continuation and explicit detour returns. |

## Extend through shared owners

| Owner | State and outcome |
| --- | --- |
| Curriculum | Encounter IDs, routes and named relationships. Reuse an encounter when its question and meaning match. |
| Session | Subject, scenario, source, clock, controls and return context. Returns restore a valid combination. Specify independent settings that keep newer choices. |
| Presentation and effects | Show the selected state within source limits. Add questions through content and existing effects. Put new behavior and domain calculations in their owners. |

- **Extension** · Plain data and small functions when several concrete stories need them. Add a route without session-engine edits. Extract observed repetition. Require a demonstrated need for an editor, DSL or cross-domain engine.
- **Time and identity** · Distinguish samples, seconds, normalized progress and domain steps. Name conversions and event owners. Keep the selected case across clock comparisons. Label renderer markers and source events by origin.

## Preserve evidence boundaries

- **Evidence** · Label computation, recorded replay and teaching illustration. A source sample establishes recorded behavior. A teaching trajectory needs separate clinical evidence before any forecast claim.
- **Unavailable results** · Show missing or unmodeled state explicitly. Retry retains the selected case.
- **Visual meaning** · Tie legends and values to marks. Pair color with labels, shapes or line styles. Use 3D for spatial questions. Choose simpler views where clearer.
- **Technical detail** · Optional role-named pseudocode shows **Input → Process → Output** with inspectable values. Disclose it and raw values behind named controls when the main result is already visible.

## Acceptance

- **Interaction** · Verify a representative encounter before extending its pattern. Then check promised effects, route returns, reload, retry, keyboard and narrow layout. Inspect terminology, input/result visibility and map continuity.
- **Learning** · Observe the reader choosing a next action, identifying change and invariants, explaining the relationship by words or pointing, applying it to a nearby case and returning after a detour. Record assistance and confusion. Let the reader stop.
- **Verdicts** · Report numerical, visual and learning evidence separately. Clicks, visits, completion and elapsed time alone cannot establish comprehension. Treat a new domain as a transfer trial.
